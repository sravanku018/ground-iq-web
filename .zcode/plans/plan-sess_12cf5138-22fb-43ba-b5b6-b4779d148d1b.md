## Context

Field surveyors and admins currently retype their password on every login; the fingerprint option (APK device-token / passkey) isn't always available (dirty hands, sensor failures, web browsers without passkeys). Add a **4-digit PIN quick-login**, per-account **opt-in**, alongside the existing fingerprint — for both the **field app** (`/field`, works inside the APK webview too) and the **Client Admin portal** (`/admin`). Per your requirement: PIN is never a default — the password/fingerprint buttons stay primary, and the PIN option appears **only for accounts that chose to set one**.

## Design decisions

- **Hashing**: reuse `crypto.ts` pbkdf2 (SHA-256, 600k iterations, per-user salt) — string-in/out, works for a PIN. The hash never leaves the server; online brute force is slowed to ~0.5 s/attempt and locked out after 5 misses.
- **Per-user lockout**: 5 consecutive wrong PINs → `pin_locked_until` (15 min) → "PIN locked — sign in with your password". Success resets the counter. Per-IP rate limit (`auth:${ip}`) stays as on every login path.
- **Storage**: `app_users.pin_hash TEXT` (nullable), `pin_failed_attempts INTEGER DEFAULT 0`, `pin_locked_until TIMESTAMPTZ` — migration `2026-11-21.1` (encrypted backup first, per policy).
- **Opt-in visibility**: login payloads (`login`, WebAuthn, `me`) carry `has_pin`; the login screens remember the last username per portal (localStorage) and show the PIN button only when that account has a PIN. Password/fingerprint buttons always remain visible.

## Backend (hono-api/legacy/handler/)

- **`lib/schema.ts`** — 3 columns + SCHEMA_VERSION bump; role constraint untouched.
- **`routes/auth.ts`** (same file as the device-token flows) — 3 endpoints, all rate-limited `auth:${ip}`:
  - `POST /api/auth/pin/setup` — requires an active session; body `{pin}` exactly 4 digits; stores hash; audit `pin_setup`; response never echoes the hash.
  - `POST /api/auth/pin/login` — body `{username, pin, expected_role}`; lockout check → verify (`verifyPassword`) → active + expected_role gates (same as password login: surveyor → field app, admin/sub → portal, super_admin excluded) → 30-day session + `has_pin` in payload; wrong PIN increments `pin_failed_attempts` (423 with remaining attempts at 5); audit `login_pin`.
  - `POST /api/auth/pin/disable` — requires active session; clears hash/attempts; audit `pin_disable`.
- **`lib/users.ts`** — `USER_COLUMNS` += `u.pin_hash`; `getUser()` maps `me.has_pin = !!u.pin_hash` (the hash itself never reaches the client).
- **`lib/webauthn.ts` authUserPayload + `routes/public.ts` login payload** — `has_pin: !!u.pin_hash` added to both builders (login SELECT gains `pin_hash IS NOT NULL AS has_pin`).

## Frontend (src/)

- **`src/components/PinPad.jsx`** (new) — shared 4-box PIN input (numeric keypad on mobile, paste-safe, auto-advance) used by both login screens and setup.
- **`src/api.js`** — `pinSetup(pin)`, `pinLogin(username, pin, expected_role)`, `pinDisable()`.
- **`src/Login.jsx`** (surveyor/field) — remembers last username (`esurvey_last_username_field`); quick-login block gains "Enter 4-digit PIN" **only when the remembered username has a PIN** (cached `esurvey_has_pin_<username>`); PIN pad → `pinLogin(username, pin, 'surveyor')` → same session/role handling as password login.
- **`src/AdminLogin.jsx`** — same pattern for admins (`expected_role 'admin'`, remembering `esurvey_last_username_admin`); Super Admin console (`superAdminOnly`) excluded from PIN.
- **`src/components/PinCard.jsx`** (new) — set / change / remove PIN (requires being signed in; asks for the PIN twice on set).
- Mounts: **`AdminProfile.jsx`** (admins, non-super) and **Surveyor profile** (`SurveyorApp.jsx` profile tab, next to Biometric/Passkey cards).
- PIN stays non-default everywhere: fingerprint/passkey buttons render first; PIN appears only for opted-in accounts.

- Staging: deploy (backup first per policy) → curl `pin/setup` → wrong PIN ×5 → 423 locked → correct PIN → session + `has_pin:true`; expected_role gating (admin PIN login rejected on the field app and vice versa); disabled account rejected.
- Headless UI check on staging: PIN button appears only for opted-in accounts on both login screens.
- Production: backup → deploy → live smoke (setup + PIN login on a test account) → payload `has_pin` verified.
